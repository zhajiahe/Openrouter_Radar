# UI 设计规范（OpenRouter Radar）

> 适用于 Web 端 React + Vite 的所有新页面、组件和 UI 变更。保持轻量、不引入重型组件库；以可扫描的监控数据、真实状态和可访问性为先。

## 1. 设计原则

1. **信息优先**：价格、单位、Provider、采集时间、数据是否过期要清晰可见；不要用装饰性动画稀释密度。
2. **状态真实**：区分首次未同步、采集中、数据过期、上游错误、真正的价格变动；绝不把采集失败展示为 Provider 下线。
3. **可访问**：键盘可操作、焦点可见；颜色不能单独表达涨跌；错误/成功提示有语义；界面默认中文。
4. **移动优先**：关键订阅操作在手机上仍然可完成，宽表格允许容器内横向滚动。
5. **部署者与订阅者分离**：绝不出现要求终端用户输入 OpenRouter API Key 的表单。

## 2. 设计 Token（唯一新增颜色入口）

基础 Token 位于 `web/src/tokens.css`，由 `web/src/style.css` 导入。新增组件使用语义变量，避免引入新的任意十六进制颜色。

- 页面背景：`--radar-bg`；侧栏：`--radar-sidebar`；顶栏：`--radar-topbar`；卡片：`--radar-surface`。
- 主文字：`--radar-text`；次级文字：`--radar-text-muted`；更低优先级元数据：`--radar-text-tertiary`。
- 品牌青绿色：`--radar-accent`，深绿视觉底板：`--radar-hero`，浅色雷达强调色：`--radar-hero-accent`；键盘焦点：`--radar-focus`；边框：`--radar-border`。
- 状态语义：`--radar-success`（健康/下降）、`--radar-warning`（过期/等待）、`--radar-danger`（失败/上涨）。
- 间距使用 4 px 基准：`--radar-space-1/2/3/4/6/8`，对应 4/8/12/16/24/32 px。
- 控件与卡片圆角分别使用 `--radar-radius-control` 和 `--radar-radius-card`。

新版工作台（2026-10）采用 **深绿侧栏 + 柔和浅灰背景 + 白色数据卡片 + 单一青绿色主操作** 的设计语言，视觉升级完成后应优先复用语义 Token，避免页面自行硬编码色板。低对比度元数据不得用于重要价格、告警和错误信息。

## 3. 布局、文字与响应式

- 桌面端侧栏约 252 px；主内容最大宽度 1580 px。白色面板、低对比边框和规律间距组织数据，避免密集描边。
- `≤ 970 px` 时，指标卡调整为两列，模型目录与详情纵向排列；扫描进度和事件列表也改为上下布局。
- `≤ 700 px` 时，导航转顶部可横向滚动，仪表盘简化为单列内容（指标采用两列），页面边距减少；表格仅在内部横向滚动。
- 标题层级使用 `h1 → h2 → h3`；正文可读尺寸优先 14–16 px，说明文字一般不低于 12 px。
- 价格必须明确单位：Token 价格统一展示 `USD / 1M tokens`；不可将其他计费维度标成每百万 Token。
- 时间戳必须注明采集/发现含义；无法确定采集状态时显示未知，不伪造“实时”。

## 4. 核心组件行为

- **导航**：使用语义 `nav`，当前页面通过 `aria-current="page"` 标识。
- **表单**：文本控件有可见 `label`，且用 `htmlFor` / `id` 建立关联；搜索等例外至少有 `aria-label`。禁用态必须说明原因。
- **按钮**：主操作使用 `.primary`，次操作使用 `.outline-button` 或 `.text-action`；危险操作使用 `.delete` 且提供确认。
- **反馈**：请求失败用 `role="alert"`；成功和数据状态用 `role="status"`；异步操作展示处理中并防止重复提交。
- **空态**：明确说明是无数据、尚未采集，还是账户未登录，并给出可执行的下一步。
- **价格趋势**：上涨/下降同时展示文字或箭头与颜色；颜色仅作辅助；长期历史只来自真实快照。
- **交互区域**：触摸设备优先保证足够的点击区域，使用 `:focus-visible` 焦点环；尊重 `prefers-reduced-motion`。

## 5. 上线前 QA 清单

1. 桌面 1440 px、平板 768 px、手机 375 px 页面均无不可操作的遮挡。
2. Tab / Shift+Tab 顺序合理，Enter/Space 可操作，焦点环可见；弹窗需具备焦点管理。
3. 测试未登录、注册关闭、无数据、加载中、异常、数据过期与正常状态。
4. 检查 AA 级文本对比度（普通文字 4.5:1、大文字 3:1），以及中文/英文长模型 ID 的换行。
5. 对比同一数据在目录、详情、事件、邮件/RSS 中的单位与时间含义。
6. 本地运行 `npm run check`，审阅截图或实际界面，确保没有引入终端用户密钥输入或无来源报价。

该规范是持续改进目标；现有旧页面未必完全符合所有建议。新增和修改的 UI 应首先遵守。

## 6. 视觉与交互一致性（第二版工作台）

- **品牌色层级**：深绿仅用于左侧栏和总览 Hero，大面积内容用浅背景与白色表格卡片，主操作统一用 `--radar-accent`。不使用高饱和霓虹渐变和伪实时行情。
- **首页信息流**：一句话说明价值 → 四张真实 KPI → 实际变化历史 → 全量 Provider 扫描覆盖。首屏能看到“是什么、多少、下一步”。
- **模型目录**：每项同时展示易读名称和原始 ID；选中项的背景/边框与 `aria-pressed` 同步；长 ID 换行，不允许撑破页面。
- **数据状态**：覆盖率来自 `provider_scanned / provider_total`，有明确分母；不是采集率承诺。上游采集失败不得展示成价格变化或端点下线。
- **价格/时间**：使用等宽数字、明确计价单位，展示的日期标明是采集时间或事件发现时间。
- **排版和留白**：主标题 28–50 px，面板标题 13–20 px，正文优先 12–14 px，低优先级提示 10–11 px；中文行高至少 1.5。
- **响应式验收**：在 1440、1024、768、390、375 px 检查总览、目录、详情和表单；设备没有鼠标时仍可选择模型与提交提醒。
- **易访问性**：表格沿用 `thead` / `tbody`，雷达装饰用 `aria-hidden`，进度条提供文本说明与 `role=progressbar`；沿用 `:focus-visible` 和 reduced-motion。
